CRITICAL
========

C1 — A RAM/Director can read any territory's or region's data
-------------------------------------------------------------

Severity: Critical (data leak - the thing the assignment weights most).

Row-level security is enforced by RLS policies that read session variables
(app.current_territory, app.current_region) which the backend sets per request. But
the LLM-generated SQL runs in the same transaction and can overwrite those variables
by calling set_config(...) inside a SELECT. The policy then reads the attacker's value.

Confirmed on the rebuilt database, logged in as Amy Nguyen (RAM, New York Metro):

| Query intent | Should return | Actually returned |
| Own territory sales count (baseline) | 136,921 | 136,921 OK |
| Texas rows via set_config('app.current_territory','Texas',true) | 0 (denied) | 8,736 Texas rows |
| Become director/West via set_config | 0 (denied) | 39,072 West-region rows |
| Loop all 15 territories in one query | own only | every territory's data |

Example payload that leaks Texas data as a New York RAM (passes the current guard):
SELECT t.n FROM (SELECT set_config('app.current_territory','Texas',true) AS x) c
CROSS JOIN LATERAL (SELECT count(*) AS n FROM sales WHERE c.x IS NOT NULL) t
WAC stayed protected (that's a column GRANT, not a GUC), so pricing did not leak - but
territory/region isolation is fully bypassable.

Fix (verified - closes all four bypass variants, allows all legitimate queries):
set_config() has no legitimate use in an analytics query. Reject it (and its read
sibling, and SET/RESET) in backend/app/sql_guard.py. Add near the other patterns:
_FORBIDDEN_FUNCTIONS = re.compile(
    r"\b(set_config|current_setting|pg_sleep|dblink|lo_import|lo_export)\b",
    re.IGNORECASE,
)
and in validate_and_finalize, after the forbidden-tables check:
    if _FORBIDDEN_FUNCTIONS.search(cleaned):
        raise SqlValidationError(
            f"forbidden function in: {cleaned!r}",
            "That question can't be answered from the data available to you.",
        )
I ran all four attack payloads and two normal queries (top-accounts, market-share)
through this: all four attacks blocked, both legitimate queries allowed.

Worth telling the reviewers, since it's an honest design note: RLS keyed on
session GUCs is inherently fragile precisely because the executed query shares the
session. The guard block is the pragmatic fix; the more robust pattern (out of scope for
the deadline) is to not execute untrusted SQL in a session that carries overridable
scope, e.g. enforce scope through the connection/role itself.

C2 — "Default to last 3 months" is force-applied to queries that already have a period
--------------------------------------------------------------------------------------

Severity: Critical (wrong answers to ordinary questions).

sql_guard.ensure_default_period() injects mo_offset IN (0,1,2) into any query that
touches sales and has no mo_offset/wk_offset filter. But it treats queries that
filter by period_qtr, period_mo, transaction_date, week_ending_date, or explicit
"all time" as if they had no period - and jams R3M on top of them. Verified results of
the current code:

| Question | What the app builds | Result |
| "Compare Q1 2026 vs Q1 2025" | adds mo_offset IN (0,1,2) AND period_qtr IN (...) | empty (no Q1 rows are in the last 3 months) |
| "Total sales all time" | adds mo_offset IN (0,1,2) | silently only last 3 months |
| "Sales in 2025" (date range) | adds mo_offset IN (0,1,2) | empty / wrong |
| "How many transactions are there?" (a reviewer sanity-check of the 2M rows) | adds mo_offset IN (0,1,2) | ~154,000, not 2,000,000 |

Fix (verified): only inject the default when no period/date column is present.
In sql_guard.py, broaden the "already scoped" check:
_PERIOD_PRESENT = re.compile(
    r"\b(mo_offset|wk_offset|period_qtr|period_mo|period_wk|"
    r"transaction_date|week_ending_date)\b",
    re.IGNORECASE,
)
and in ensure_default_period, gate on _PERIOD_PRESENT instead of _OFFSET_COLUMN
when deciding whether a scope already has a period filter. I re-ran the four broken cases
above plus "no-period top accounts" and "already-R3M": the first three now pass through
untouched, the genuinely period-less "top accounts" still gets R3M, and the already-R3M
query is unchanged.

Remaining nuance to decide: an explicit "all time" / "total ... ever" should scan all
history, but a pure regex can't read intent. Cleanest is to have the SQL-generation step
emit a marker when the user named no period (e.g. prepend -- NO_PERIOD) and default only
then - intent comes from the model, not a post-hoc guess. Short of that, the fix above at
least stops corrupting the many queries that _do_ name a period.

H1 — Out-of-scope questions get a fabricated "no sales… market conditions" answer
---------------------------------------------------------------------------------

When a RAM/Director names another territory/region, RLS correctly returns 0 rows - but the
answer model then invents a business reason. Live examples from the repo's own TESTS.md:

- RAM, "Show me sales in California South" -> *"There were no sales recorded in California
  South… due to market conditions, product availability…"*. California South actually had
  23,410 units that period.
- Director, "Show me sales for the West region" -> "no sales… due to market conditions".
  West region actually had 124,512 units.

Two problems: it's misleading (implies zero business, not zero access), and it leaks
the fact that the territory exists while masking that access was denied. Should instead
say access is limited to their own scope and offer to run it there. Detect a named
territory/region outside the user's scope (you already have the user's scope and
zip_territory) and return an access message rather than passing an empty result to the
answer model.

H2 — "This year" / "YTD" is defined as trailing 12 months, then mislabelled
---------------------------------------------------------------------------

DOMAIN_RULES rule 5 defines "this year"/"year to date" as mo_offset BETWEEN 0 AND 11
(Oct 2025-Sep 2026), which is a trailing 12 months, not year-to-date. Then the answer
text calls it "January to November" (TC02) - a period that is neither the query's window
nor real (data ends Sep 2026). Verified impact: Cyclonova "this year" reported as
$373.7M; true Jan-Sep 2026 is $277.5M. Fix: define YTD as period_mo >= '<year>-01'
(current calendar year to latest month) and let periods.py label it from the actual
period_mo values rather than a hardcoded phrase.

H3 — Market share (and other ratios) printed 100× too small
-----------------------------------------------------------

Severity: High (the headline competitive metric is misreported).

Live, Exec: Zenovax Docetaxel market share computed correctly as 1.1378 but was
rendered as "1.14%". A decimal share of 1.1378 is 113.78%, not 1.14%. The
answer step is treating the already-decimal ratio as if it were a raw fraction needing no
x100, or mislabelling it. Two consequences: every market-share answer is wrong by a factor
of 100, and the genuine >100% anomaly (which DESIGN.md correctly explains as a property of
the synthetic market_data) is hidden instead of surfaced. Fix: in the answer prompt (or a
formatting step) multiply decimal shares by 100 for display, and when a share exceeds 100%,
state the caveat rather than masking it.

H4 — Quarter / year comparisons generate invalid SQL (hallucinated columns)
---------------------------------------------------------------------------

Severity: High (a whole class of common analytics questions fails).

Live, Exec: "Compare Zenovax Q1 2026 vs Q1 2025" produced SQL referencing
s.period_qtr = 'Q1' and s.period_yr = 2026. Neither is right: period_qtr is stored as
'2026-Q1', and there is no period_yr column at all, so the query errors and the user
gets the generic "too complex or slow" message. Any "Qx YYYY vs Qx YYYY" or year-over-year
comparison is affected. Root causes: (a) the schema summary in the prompt lets the model
guess a year column; (b) C2 then also injects R3M on top. Fix: add a worked few-shot example
for calendar-quarter and year-over-year comparisons using the real period_qtr values
('2026-Q1', '2025-Q1'), and fix C2 so it doesn't compound the error. The "too complex or
slow" message is also misleading - the query didn't time out, it referenced a missing column;
consider surfacing invalid-column errors distinctly.

============
MEDIUM / LOW
============

- M1 - HTTP only. The site serves login over plain http://, so the shared password
  crosses the network unencrypted, and a security-minded reviewer will notice. Put it
  behind HTTPS (Caddy/Nginx + a free cert on a hostname, or an ALB). Low effort, good
  optics for a security-weighted brief.
- M2 - Drug names misspelled in answers ("CYCLONEVA", "GEMMARA", "GEMTARA"->"GEMMARA").
  The SQL is right; the answer model is paraphrasing names. Tell the answer prompt to copy
  product names verbatim from the rows.
- M3 - Director revenue question isn't offered a volume alternative. TC08: a Director
  asking for revenue gets a flat refusal; the spec asks to offer volume instead. The RAM
  path does this; align the Director path.
- M4 - Exec occasionally told "scoped to your region." Answer-side only (the data is
  full company); still wrong for an Exec and undercuts trust. Tighten the answer prompt's
  scope-note rule.
- L1 - /docs (FastAPI interactive API) is public on the live host. Harmless but
  unnecessary surface; disable in production (FastAPI(docs_url=None, redoc_url=None)).
- L2 - org_scope is readable by every role (acknowledged in DESIGN.md). A RAM can
  enumerate all 40k org->territory mappings. No sales/pricing leak, but note it.
- L3 - DEFAULT_DEMO_PASSWORD committed in tests/qa_regression.py. Fine for a
  throwaway demo and documented, but rotate/remove before this repo is shared wider.
